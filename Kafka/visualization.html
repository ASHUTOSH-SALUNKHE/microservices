04 · Replication factor and leader–follower behavior

A broker is a server. Leadership is per partition, so the same broker can lead several partitions while following others.

If the leader fails, Kafka may elect an eligible in-sync replica. Replication factor 3 means three copies total; it does not mean three leaders.

Followers fetch the leader's log and replicate records. They do not independently lead that same partition at the same time.

05 · Producer acknowledgements (acks)

Choose an acknowledgement mode and read what the producer knows when its send completes.

Example replication factor = 3min.insync.replicas = 2
acks=all: wait for the leader and all replicas currently in the in-sync replica set (ISR) to acknowledge the write. With min.insync.replicas=2, at least two ISR members must be available for an all-acks write to be accepted.
acks=0Producer does not wait for a broker acknowledgement. Lowest confirmation overhead, but it cannot know from an ack whether the record was written.
acks=1Wait for the partition leader to acknowledge its local append. A leader failure before replication can risk losing the acknowledged record.
acks=allWait for acknowledgements from the current ISR. Pair with a suitable replication factor and min.insync.replicas for stronger durability. “All” means all ISR, not necessarily every configured replica if one is out of sync.

07 · Retention vs log compaction

Retention decides which old data can be deleted. Compaction preserves the latest known value per key over time; it is not an immediate in-place update.

Topic log · cleanup.policy=delete

off 0key=order-1001 · OrderCreated
off 1key=order-1002 · OrderCreated
off 2key=order-1042 · OrderCreated
off 3key=order-1047 · OrderCreated
Time / size based cleanup

Old log segments become eligible for deletion

For event streams such as orders.created.v1, a common policy is time-based retention, for example 7 days. Consumers must process within the retention window or use an appropriate replay/source strategy.

cleanup.policy=delete
retention.ms=604800000
Kafka deletes eligible log segments, not each individual record at an exact second. Offsets are not renumbered after cleanup.

08 · One complete event lifecycle

Connect the concepts: key, partition, replication, acknowledgement, consumption, committed offset and lag.

STEP 01

Order is created

Order Service writes its DB transaction and outbox event, then the relay sends a record to Kafka.

STEP 02

Partition is selected

Record key order-1042 is hashed by the configured partitioner; the producer sends to that partition's leader.

STEP 03

Record is replicated

The leader appends at a partition offset; follower replicas fetch the log. The configured acks mode governs producer confirmation.

STEP 04

Group processes it

Each consumer group reads independently, processes work, and commits progress. End offset minus committed position gives approximate lag.

Production note: Kafka transactions, idempotent production, an outbox pattern, idempotent consumers, retry topics and dead-letter topics solve different reliability problems. Kafka delivery and database side-effects are not automatically one atomic transaction just because the message is in Kafka.

09 · Quick glossary

Keep these distinctions clear when designing or discussing a real Kafka system.

BrokerA Kafka server that stores partition replicas and serves client requests.
TopicA named stream/category of records, such as orders.created.v1.
PartitionAn ordered log within a topic; distributes storage and consumer parallelism.
Leader replicaOne replica per partition at a time; normal producer writes go to it.
Follower replicaCopies the leader's log and can be eligible for leader election.
OffsetA record's position in one partition's log, not a topic-wide/global ID.
Record keyOptional key often used for partitioning related records and preserving their per-partition order.
Replication factorTotal replicas of one partition, including its leader.
AcknowledgementProducer's configured rule for when a send is considered successful.
Consumer groupConsumers sharing work and committed progress for a topic subscription.
Consumer lagHow far a group's committed/processed position trails the partition end.
Retention / compactionDelete old data by time/size versus retaining the latest record per key over time.
KRaftModern Kafka's built-in metadata quorum/coordination mode, removing ZooKeeper dependency.
ZooKeeperCoordination service used by older Kafka deployments; not the broker and not in the normal record path.
Consumer offsetThe group's stored next-read position for a partition; separate groups have separate offsets.
ISRIn-sync replicas considered sufficiently caught up for the configured replication protocol.
